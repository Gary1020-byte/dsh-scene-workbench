# 設計

> **為什麼走 DSH 原生、而不是繼續養 Electron 外殼。**

---

## 一、三個進程，兩套東西

官方說法（`luanyujia-workbench/04-工作台搭建/技术栈与启动链路.md`）：

```
① 壳（Electron main）      建窗口、管場景、連 IPC、拉起引擎
② 渲染層（頁面）            renderer/*.js + renderers.js（各面板實作）
③ 本地引擎（HTTP 3080）      會話、模型調用、技能、插件、MCP
④ MCP 子進程               工具能力的實際執行者
```

> **「界面白」和「AI 不回答」是兩類完全不同的故障**——因為 ①② 和 ③ 是兩套東西。

**關鍵認知**：① 與 ② 是**外殼**；③ 是**引擎**。
引擎本來就在跑（本機 3080，而且已用 Tailscale 對外公開），
**外殼只是另一層皮**。而且外殼自己也嵌了引擎的 web UI（`場景 0`）。

⇒ **要做的工作台，能力在引擎；缺的只是「場景」這層介面。**
⇒ 而引擎是 **Cordis 插件系統**，本來就是設計來被 patch 的：

```
dsh --profile <name>            啟動 profile（一疊 plugin-bundle patch 層）
dsh --patch <path>              加一層覆蓋
dsh plugin --profile <p> add    裝插件進 profile
```

## 二、場景這件事，引擎已經做完 90%

| 場景要素 | 引擎怎麼做 | 誰做 |
|---|---|---|
| 獨立工作目錄 | `dsh-working-directory` | ✅ 引擎 |
| 場景憲法（`AGENTS.md`） | 按 cwd 的 `.git` 根自動注入 | ✅ 引擎 |
| 場景專屬技能（`.dsh/skills/`） | 按 cwd 的 `.git` 根自動發現 | ✅ 引擎 |
| 常駐會話 | 一條 session | ✅ 引擎 |
| **記憶檔與交接** | 檔案（在 cwd 裡） | ✅ 檔案層 |
| **場景清單的呈現** | ← **沒有** | ❌ 外殼在做 |
| **面板網格** | ← **沒有** | ❌ 外殼在做 |
| **場景分頁列** | ← **沒有** | ❌ 外殼在做 |
| **跨場景派單／回執** | ← **沒有** | ❌ 工具在做 |

⇒ **外殼真正提供的是三樣 UI ＋ 一套工具。**
本 repo 只做「UI 那一半」；派單／回執那一半屬於方法論 repo（引擎中立）。

## 三、★ 取捨：面板網格沒有等價插槽

**這是走原生路徑最誠實的一個代價。**

| | Electron 外殼 | DSH 原生 |
|---|---|---|
| 場景分頁列 | 有（自製 tab bar） | 有 slot：`conversation.session.header.leading` |
| 右側分頁 | 有 | **有原生 slot**（`sidebar.right.pane.tab`） |
| **面板網格** | 有（自製 grid） | **沒有**——最接近的是 `shell.overlay`（全螢幕覆蓋） |
| 3D 記憶神經元 | 有 | 要用 overlay 重做，或放右側分頁 |

官方規格擋掉了「自己造版面」：

> 「選一個**已經分配空間**的插槽」
> 「不要替換 app root，也不要往 `document.body` 再掛一個應用程式」

⇒ **面板網格要嘛用 `shell.overlay` 重做，要嘛放棄網格、改用分頁。**

**本 repo 的取捨：先放棄網格。**
理由：網格是「呈現」，派單／回執／路由是「能力」。
**先把能力接上，網格之後再說**——而且 overlay 是可行的退路，不是死路。

## 四、為什麼 v1 是「純 Client」

官方規格的第一條原則是：

> 「先交付一個能跑的插件……**先裝上**，再做視覺打磨。」

而「能跑」的最小充分條件是：**分頁出現 ＋ 讀到真實資料**。
場景清單完全由引擎既有的 `sessions` ＋ `workspaceFiles` 算出來，
⇒ **不需要 Host 側任何東西**（`index.js` 留空）。

**好處**：
- 套件小、可讀、好審
- 不碰 profile 設定（`config: {}`）
- 之後要接 Host（場景設定檔／路由表／派單）時，`index.js` 加 `apply(ctx, config)` 就行，
  patch 那一列補 `config`（**記得 config 是整份取代，不是深合併**）

## 五、驗收怎麼做

> 官方規格：「安裝與 slot 註冊本身**不構成**使用者看到的東西。」

| 層 | 怎麼驗 |
|---|---|
| 套件有沒有裝上 | `plugin_manager list_bundles` / `list_plugins` |
| 有沒有真的啟用 | 讀回來的 `application` 欄位（不是 log、不是行程表） |
| slot 有沒有註冊 | `cordis_inspect_query` 查 Slots 的 `listSubTree` |
| **使用者看得到嗎** | **實際開著頁面看**——沒有瀏覽器控制權時，要明講「視覺未驗證」 |

> ★ 本 repo 的 README 與每次交付都照這條分層報，不會用「已安裝」冒充「已驗證」。

## 六、與方法論 repo 的分界

```
方法論 repo（引擎中立）        本 repo（DSH 專用）
  場景記憶規格                    把場景「看見」出來
  派單／回執契約                  ← 只讀，不定義
  路由表規格
  驗收工具（引擎中立）
        ↑ 讀同一批檔案
```

**規格在檔案裡；本 repo 只讀檔案。** 換引擎時，方法論 repo 不用改，
本 repo 要重寫——**這正是「引擎中立」的意思**。
